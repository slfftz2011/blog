在写第一行代码之前，有件事比装编辑器更重要：知道自己正在学的东西**能干什么，不能干什么**。这一节不教具体语法，只干三件事——把前端三件套的分工说清楚，把静态开发的地盘划出来，再把整个系列的地图摊开给你看。

不过别急，咱先从你每天都在经历的一件事说起。

## 先看一个场景：你打开了一家咖啡店的主页

假设你朋友发给你一个链接：“这家手冲咖啡店不错，你看看。”你点开，手机屏幕上出现了一个页面：

- 最上面是店名“山腰咖啡”，下面一行小字“自家烘焙 · 每周二休息”；
- 中间一张大图，是咖啡师在冲咖啡；
- 图片下面三行文字，分别写着“手冲耶加雪菲 ¥28”“冷萃美式 ¥22”“燕麦拿铁 ¥26”；
- 再往下有一个按钮“查看菜单”，你点了一下，页面“唰”地滑到了菜单区；
- 你试着在“留言板”里打了一行字，点“提交”，它提示“留言成功”。

整个过程你大概花了十秒，啥也没多想。但这十秒里，浏览器其实干了好几件事：它把店名当成“标题”读，把图片当成“图片”画，把价格当成“列表”排，还执行了一小段代码，让你的点击和留言有反应。

这就是 Web 的日常。而你要学的，就是怎么**亲手做出这样一个页面**。

## 三件套：HTML、CSS、JavaScript，各管一摊

任何网页，底层基本都是三样东西搭起来的。它们的全名有点唬人，但拆开看就很好懂。

**HTML——HyperText Markup Language，超文本标记语言。**
名字里的 “HyperText” 是“超文本”，意思是你写的文字里可以“链”到别的页面；“Markup Language” 是“标记语言”，意思是它用一对对“标签”给内容**贴身份牌**。比如你写 `<h1>山腰咖啡</h1>`，就是告诉浏览器：“‘山腰咖啡’这四个字是页面的一级标题，请按标题来对待。”HTML 不负责好看，它只负责**说清楚每块内容是什么**。

**CSS——Cascading Style Sheets，层叠样式表。**
“样式表”就是一张“化妆清单”；“层叠”指的是多条规则可以叠在一起，后面的可以覆盖前面的，像给同一面墙刷好几层漆。CSS 负责**决定这些东西长什么样**：标题用多大字号、什么颜色，图片圆角还是直角，手机上是一列还是两列。HTML 是骨架，CSS 是皮肤和衣服。

**JavaScript（简称 JS）——一种编程语言。**
注意，它跟 Java 是两码事，名字像纯属历史原因，好比“热狗”里没有狗。JavaScript 负责**让页面动起来**：你点按钮它响应，你填表单它校验，你滚动页面它加载新内容。HTML 和 CSS 都是“描述性”的——你写什么，浏览器就呈现什么；JavaScript 则是“命令式”的——你写一段逻辑，浏览器照着执行。

那 **MDN** 又是什么？全称 **Mozilla Developer Network，Mozilla 开发者网络**。Mozilla 就是做火狐（Firefox）浏览器的那家组织，他们维护了一个巨大的 Web 技术文档网站，HTML、CSS、JavaScript 的每个标签、每条属性、每个函数都能在里面查到用法和示例。你可以把它理解成 **Web 开发的“新华字典”**——不用背，但要会查。本系列会反复提到它，看到这三个字母别慌，就是个查资料的地方。

## 底层其实发生了什么：浏览器是个“翻译官 + 画师”

你可能会好奇：我写一堆文本，浏览器怎么就把它变成花花绿绿的页面了？

简单说，浏览器拿到一个 HTML 文件后，会干三件事：

1. **读懂结构**。它逐行读 HTML，把每个标签解析成一个“节点”，最后拼成一棵倒挂的树——这棵树有个学名叫 **DOM（Document Object Model，文档对象模型）**。你可以把它想成一份“页面户口本”，每个标题、图片、按钮都在上面登记了身份和位置。
2. **照着化妆**。它再读 CSS 规则，看哪条规则管哪个节点，算出每个东西最终的颜色、大小、位置。这一步叫“样式计算”和“布局”。
3. **画到屏幕上**。算好之后，浏览器把每个像素涂出来，你才看到页面。

而 JavaScript 呢，是在这棵树建好之后，**能去改动它**的那双手。比如你点“提交”，JS 可以往页面里插一行“留言成功”，或者把按钮暂时变灰。所以三层的关系可以记成一句话：**HTML 搭骨架，CSS 穿衣服，JS 让它动**。

## 用同一段内容，看三层怎么配合

光说概念容易飘，拿“一个按钮”举例最直观。假设我们要在页面上放一个按钮，写着“Player 1: Chris”，点了之后能改名字。

**第一层，HTML 给它身份：**

```html
<button type="button">Player 1: Chris</button>
```

这行代码的意思是：“这里有一个按钮，上面写着 Player 1: Chris。”就这么多，浏览器读到它，会画出一个灰扑扑的、系统默认样式的按钮。

**第二层，CSS 给它化妆：**

```css
button {
  font-family: "Helvetica Neue", sans-serif;
  border: 2px solid rgb(200 200 0 / 60%);
  background-color: rgb(0 217 217 / 60%);
  border-radius: 10px;
  padding: 3px 10px;
  cursor: pointer;
}
```

这段规则说的是：“所有按钮，字体用 Helvetica Neue，边框两像素、带点半透明的黄，背景是半透明的青色，圆角十像素，内边距上下三像素、左右十像素，鼠标移上去变成小手。”加完这段，那个灰按钮就变成了一个有颜色的圆角按钮。

**第三层，JavaScript 让它有反应：**

```javascript
function updateName() {
  const name = prompt("Enter a new name");
  button.textContent = `Player 1: ${name}`;
}
const button = document.querySelector("button");
button.addEventListener("click", updateName);
```

这段代码的意思是：“找到页面上的按钮，给它装一个‘点击’监听器；用户一点，就弹窗问新名字，然后把按钮上的文字换掉。”现在按钮不光好看，还能用了。

如果你暂时看不懂代码里的符号，完全正常——这一节不是让你现在就学会写，而是让你**看出三层各自在管什么**。用生活化的话再翻译一遍：

> - HTML 说：“这是个按钮，叫 Player 1: Chris。”
> - CSS 说：“按钮应该是青色的、圆角的、鼠标放上去变小手。”
> - JavaScript 说：“有人点它，就问新名字，然后把名字换掉。”

出问题时，这个分层就是你的“分锅指南”：**文字不对，先翻 HTML；样子不对，先查 CSS；点了没反应，先看 JavaScript**。分锅到户，效率高。

不过也得说句实在话：分层是个**值得追求的理想，不是铁板钉钉的现实**。JavaScript 可以实时改 CSS，现代框架会把 HTML 和 CSS 写进 JavaScript 里，实际项目里三层经常搅在一起。但正因为真实世界总会“混”，初学阶段才更要把每层的职责分开练清楚——先学会各司其职，后面才不至于混得毫无章法。

## 静态开发：能做很多事，但不能包打天下

HTML/CSS 属于“静态开发”的地基。静态站点的共同特征是：浏览器拿到的是构建时就已经准备好的文件——HTML、CSS、JavaScript、图片、字体——**没有后端服务器在请求时实时生成页面或处理数据**。

听起来限制挺大，其实静态开发覆盖的场景比你想的多：**个人主页和作品集、产品落地页、文档站、技术博客、项目演示页、后台界面骨架**，都归它管。共同点是“内容在编写时基本确定”，不需要登录、下单、写数据库。

但边界也得提前说清楚，免得后面踩坑怪我没讲。静态站点照样能跑 JavaScript，能调公开 API（比如查天气、查汇率），能用 `localStorage` 在你自己电脑上存点小状态。它真正做不到的是：**在页面发给用户之前运行你的代码**。这意味着它没法安全地藏秘密（比如私有 API Key），做不了服务端鉴权，也不能直接写数据库。需要这些能力的项目，就得请后端出场，或者借 BaaS（Backend as a Service，后端即服务）类服务帮忙。

第 1 部之所以从 HTML/CSS 开始，而不是一上来就“全栈”，原因就在这儿：**先把不需要后端就能做对的事做对**。一个语义清晰、响应式、加载麻利的静态页面，本身就是能独立交付的活儿；它也是后面所有复杂应用的底座。地基不打好，楼上装修再豪华也白搭。

## 为什么 HTML/CSS 值得认真学，而不只是“过渡一下”

很多人把 HTML/CSS 当成“随便看看，赶紧进框架”的前置任务。但有两样东西，只有在这一层才能打好：

**第一，可访问性。** 语义化 HTML 不是“加分项”，而是屏幕阅读器、键盘用户、搜索引擎理解页面的前提。一个 `<div>` 堆出来的“按钮”和一个真正的 `<button>`，视觉上可以一模一样，但对辅助技术来说完全不是一回事。可访问性意识从第一天建立，比后期回头“补”要容易得多——有些坑，早绕比晚填省事。

**第二，响应式和布局的判断力。** Flexbox、Grid、媒体查询、盒模型，这些概念在框架和组件库里会反复出现。如果原生 CSS 的层叠、优先级、文档流没搞明白，遇到框架的样式覆盖或布局异常时，基本就只剩“到处加 `!important`”这一招了。那感觉，就像螺丝刀拧不动，直接上锤子。

而且，HTML/CSS 的能力不会因为框架流行就过期。框架改变的是**组织和复用代码的方式**，不改变**内容需要结构、界面需要样式**这个事实。先理解原生，再用工具，工具才真正为你所用；反过来，工具就会替你当家。

## 五部曲地图，以及第 1 部的边界

整个系列按“从静态到动态、从原生到工具、从开发到维护”的顺序展开：

| 部 | 主题 | 解决的核心问题 |
|---|---|---|
| **第 1 部** | **HTML/CSS 结构与样式基础** | 能独立完成语义化、响应式的静态页面 |
| 第 2 部 | JavaScript 语言核心与浏览器交互 | 让页面拥有状态、交互和网络请求能力 |
| 第 3 部 | TypeScript + Vite + React | 进入组件化、类型化、模块化的现代开发 |
| 第 4 部 | Vue、模板渲染（Pug）与后端衔接 | 理解另一套框架思路，接通 API 和服务端渲染 |
| 第 5 部 | 生产构建、质量保障与项目维护 | 把项目从“能跑”做到“能上线、能维护” |

**第 1 部的能力边界**在这儿说清楚：这一部**不碰** JavaScript 逻辑、框架、构建工具、后端，也不碰 CSS 预处理器。目标只有一个——**能独立写出一个结构正确、手机和桌面上都好用、对辅助技术友好的静态站点**。这个目标不炫，但它决定了后面每一部是在“补窟窿”还是在“往上盖”。
